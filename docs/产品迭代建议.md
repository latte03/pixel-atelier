# Pixel Atelier 产品迭代建议

日期：2026-11-09。以下是基于当前本地版本的产品判断与待验证假设，不是用户调研结论。

## 建议：用少量完整模板，推动工作流迭代

先把女骑士做成可复制、可修改、可接回游戏的一份完整模板，再用另外两种角色验证这条流程。等用户能稳定完成一次修改与交付，再扩充人物数量。

可以先按约 70% 工作流、20% 样板模板、10% 真实使用观察来分配精力。这是当前阶段的资源分配建议，后续应按实测失败点调整。

用户要完成的事情是：“我喜欢这个角色包，把它改成我的主角，再补一个动作，放进自己的游戏。”只增加人物参考图，只完成了这条路径的第一小段。

## 1. 当前证据说明了什么

| 观察 | 对迭代的含义 |
|---|---|
| 已有一位女骑士和八类已有动作，可直接体验、预览和导出 | 已经有可演示样板，可以开始做完整使用验证 |
| 当前预设和装备约束围绕双手巨剑 | 多上传法师、弓手图片，不等于动作流程已适配这些角色 |
| 色板按单个动作导出时生成 | 同一人物不同动作还缺少统一的冻结规格 |
| 保存项目以单个动作为主 | 用户难以把“一个人物的一整套动作”作为一个工程管理 |
| 画坏一帧仍缺少便捷的整帧替换链路 | 有少数坏帧时，用户可能需要重新做较大的返工 |
| 本机示例没有随源码分发 | 别人安装后，可能看不到演示中最吸引人的部分 |
| 新手步骤与未保存时间轴缺少全面自动恢复 | 中断或刷新容易让用户失去上下文 |

因此，短期内最有价值的改进，是让一个用户走完整个路径，并能在失败后继续。

## 2. “人物模板”应该包含什么

建议把它定义为“角色工程模板”，同时保留三种独立规格：人物规格、动作配方、输出规格。

| 部分 | 应包含的信息 |
|---|---|
| 人物规格 | 母版、版本、头身比例、像素尺度、固定色板、服装特征 |
| 武器规格 | 类型、相对人物长度、宽度、握持位置、必须保持的结构 |
| 动作配方 | 阶段、关键姿势、时长、首尾关系、发力与惯性要求 |
| 已完成动作 | 通过检查的完整帧、源图、预览与导出 |
| 输出规格 | 画布、根节点、固定采样、方向约定、文件命名 |
| 修改规则 | 哪些能直接改，哪些必须重新生成，哪些需要重做整套动作 |
| 验证记录 | 哪些检查完成、哪些游戏中试过、尚存的问题 |
| 素材来源 | 参考与生成来源、作者、允许分享范围、版本与依赖 |

当前 `.json` 项目与模板库还不等同。现有文件可以恢复一个动作，但缺少整个人物的多动作管理、可修改范围和系统化继承关系。

## 3. 用户可以“拿过去修改”，但要区分修改深度

| 修改需求 | 合理的产品行为 | 当前基础 |
|---|---|---|
| 调整速度、停顿、位置、预览倍率 | 直接修改配方，重新导出 | 已有主要基础 |
| 改发色、盔甲颜色 | 保留一份原模板，用受控换色或重绘验证全部帧 | 尚无完整流程；不能保证改一张母版后其余动作自动同步 |
| 补一个同武器动作 | 引用冻结人物/武器规格，只生成新增动作，再检查一致性 | 可手动逐动作操作，规格继承尚未产品化 |
| 把女骑士换成另一个人 | 保留动作意图，重新生成并检查人物与比例 | 不能直接当成稳定换皮能力 |
| 巨剑换弓或法杖 | 重新设计握持、发力和攻击阶段，再生成与检查 | 需要武器专用配方，当前巨剑预设不足以覆盖 |
| 把二头身改成高比例角色 | 重新确定人物尺度、重心与动作幅度 | 不宜沿用原像素偏移或只缩放图片 |

第一版建议明确支持“调节奏、调位置、导出、同武器补动作”。把换人、换武器当作需要验证的新分支，避免向用户暗示所有模板都能一键换皮。

## 4. 先做三套有代表性的样板

保持同一像素美术系列，优先覆盖动作差异，而非发色差异。

| 样板 | 主要验证什么 |
|---|---|
| 现有双手巨剑女骑士 | 重量、惯性、下砸、上挑、长武器空间 |
| 短剑 / 轻装近战角色 | 快速起手、连段衔接、较短攻击距离 |
| 法杖角色 | 不同握持与施法节奏，人物动作与特效边界 |

这是下一轮验证样本的建议，不表示后两套已经制作完成。

每套先交付四个必要动作：待机、移动、主攻击、受击。流程通过后，再补闪身、重击、跳跃、倒地等。单纯为了展示八张卡片而堆动作，会增加用户检查负担。

暂时不要同时扩张多画风、多头身和多朝向。否则一次失败很难判断来自动作、画风还是空间规格。

## 5. 迭代顺序与验收条件

### 第一阶段：把现有样板做成完整角色工程

建议优先完成：

1. **角色工程与规格冻结**：一个人物下管理多个动作；母版、武器、色板、尺寸和锚点有明确版本。
2. **自动保存与恢复**：刷新后找回当前角色、动作、生成任务、时间轴和未完成检查。
3. **模板复制与修改记录**：复制一份女骑士工程，保留原版，知道改了哪些动作和规格。
4. **同人物跨动作色板**：支持先冻结色板，后续动作共用；同时保留来源和审核状态。
5. **可交付的示例安装**：新安装也能拿到清楚标注来源与分享范围的示例，或一键导入用户自有模板包。

验收方式：从干净安装开始，复制模板，改一个动作的节奏，保存、关闭、恢复，再导出；整个过程不编辑配置文件、不丢失进度。

### 第二阶段：降低返工成本

建议优先完成：

- 将“人物约束”和“武器动作要求”独立，按模板选择装备类型。
- 图表排版先自动提出建议，用户确认后切帧；保留手动修正入口。
- 标记坏帧，只重生成对应完整姿势，支持替换、前后对照与撤销，不拆身体关节。
- 增加可解释的检查：空帧、裁切、尺寸、色板、重复帧、逻辑锚点。人体发力与剑长审核仍需单独验证。
- 对同一套动作提供一致的游戏预览环境，并提供一个目标引擎的导入适配。

验收方式：新用户能找到一帧错误，完成替换，确认其他帧没有被连带改坏，再导出并验证。

### 第三阶段：按真实需求扩充模板

再增加人物、装备、动作配方与特效组合。每个模板都附“能直接改什么、哪些需要重新生成”的说明。

验收方式：新增一套模板主要靠填写规格、放入素材和验证，不需要为每个人物修改前端代码或重写一套处理流程。

## 6. 用真实使用结果决定是否扩库

先找约 5 位目标用户做一轮小规模观察。这是发现阻碍的测试，不代表能够统计整体成功率。

给每位用户同一个任务：

> 复制一个模板，改成自己想要的战斗节奏，补充或修正一个姿势，导出并放进一个简单游戏场景。

记录这些节点：

| 记录项 | 反映的问题 |
|---|---|
| 首次成功导出用了多久 | 新手路径是否清楚 |
| 需要几次生成、多少次重试 | 成本和可控性 |
| 因什么返工、改了几帧 | 质量缺口在哪里 |
| 哪些步骤需要口头指导 | 页面还没解释清楚什么 |
| 能否关闭再继续 | 工作是否可恢复 |
| 是否进入实际游戏 | 交付格式与引擎适配是否成立 |
| 完成后最想补什么 | 应扩充哪类模板或流程 |

判读方式：

- 多人卡在第一次生成、切帧、恢复或导出：继续修工作流。
- 大部分人能完成，但觉得角色太少、类型不合适：扩模板。
- 经常换人后形象走样：优先做人物规格与跨动作一致性。
- 导出顺利但放进游戏后不能用：优先做游戏预览、事件与引擎适配。

可以给下一轮设一个内部目标，例如 5 人中至少 4 人能在少量提示下完成示例修改与导出。这是自己设的通过条件，不是当前已经达到的结果。

## 7. 下一轮最值得做的具体版本

建议范围：**角色工程 + 复制现有女骑士模板 + 自动保存 + 多动作统一规格**。

让用户完成这一条路径：

```text
选中女骑士模板
  → 复制成自己的工程
  → 查看整套动作和已冻结规格
  → 修改连段节奏 / 补充一个动作
  → 对照母版检查
  → 保存并恢复
  → 导出整套资源
```

这条路径完成后，再用短剑与法杖角色检验通用性。模板数量可以增长，同时每一套新模板也在检验工作流是否需要继续改进。

当前不建议优先投入：大量只有立绘的人物、一次批量生成全部动作、更多装饰性界面、直接开放陌生人远程使用本机桥接。这些都不能代替一次可靠的角色工程交付。
